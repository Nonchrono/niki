# Niki Journal Google Drive 연동 설계

> 이 문서는 이전의 복구 구문 기반 설계 초안입니다. 현재 구현은 동기화 키를 같은 Google Drive 앱 데이터 폴더에 자동 보관하므로 아래의 종단간 보안·복구 구문 설명은 현재 동작과 다릅니다.

## 현행 구현 참고

현재 앱은 Google Drive `appDataFolder`에 난수 동기화 키를 자동 보관합니다. 따라서 같은 계정으로 연결한 기기가 수동 복구 키 없이 기록을 복원하지만, Google 계정 접근 권한이 있으면 키와 기록 모두에 접근할 수 있어 종단간 암호화로 간주하지 않습니다. 아래의 복구 구문 및 SQLite 계획은 구현된 기능이 아닙니다.

기록 리비전은 업로드 전에 로컬 저장소에 남겨 전송 후 체크포인트가 실패해도 같은 리비전으로 재시도합니다. 별명 초기화와 일지·템플릿 삭제도 원격 리비전으로 전파합니다. 일지·템플릿을 두 기기에서 동시에 수정한 경우 원격 값을 원래 항목에 두고 이 기기의 값은 복사본으로 보존합니다. 해독·검증에 실패한 파일은 자동으로 건너뛰지 않고 설정 화면에서 사용자가 명시적으로 건너뛰거나 다시 확인할 수 있습니다. 자동 동기화는 앱 프로세스가 실행 중일 때만 동작합니다.

## 목적

Windows 앱의 기록을 로컬에 먼저 저장하고, 사용자가 선택하면 자신의 Google Drive로 암호화된 변경 사항을 동기화한다. 다른 PC에서 같은 Google 계정과 복구 구문으로 기록을 복원할 수 있어야 한다. 앱은 Google Drive 용량이나 API 사용에 대한 요금을 청구하지 않는다. 다만 사용자의 Drive 저장 용량 및 Google의 API 한도는 적용된다.

## 사용 방식

1. **기본 상태:** Drive 연결 없이 로컬 작성·검색·백업을 모두 사용한다.
2. **연결:** 설정 > Google Drive > 연결에서 시스템 브라우저로 Google 동의를 연다. 연결 전 필요한 권한과 저장 위치를 보여 준다.
3. **동기화:** 연결 후 로컬 변경을 암호화해 업로드하고 원격 변경을 내려받는다. 오프라인에서는 로컬에 기록하고 재접속 시 재시도한다.
4. **복원:** 새 PC에서 연결하고 복구 구문을 입력하면 일지·글·첨부를 내려받는다. Google 계정만으로는 암호문을 해독할 수 없다.
5. **보이는 백업:** 별도 선택 기능으로 사용자가 직접 볼 수 있는 Drive 폴더에 암호화 백업을 만든다. 일반 동기화 저장소와 권한을 분리한다.
6. **연결 해제:** OAuth 토큰을 지우고 동기화를 멈춘다. 로컬 기록은 유지한다. Drive 파일 삭제는 별도 명시적 동작으로만 한다.

## Google API와 권한

| 목적 | 권한 및 저장 위치 | 이유 |
| --- | --- | --- |
| 개인 기록 동기화 | `https://www.googleapis.com/auth/drive.appdata`, 숨겨진 `appDataFolder` | 앱 자체 데이터만 다루는 비민감 범위. 다른 Drive 파일을 읽을 권한이 없다. 사용자의 Drive UI에는 보이지 않는다. |
| 사용자가 볼 수 있는 백업 | `https://www.googleapis.com/auth/drive.file`을 포함한 별도의 전체 재인증 | 앱이 만들거나 사용자가 앱과 공유한 파일에 한정한다. 기존 Drive 전체 접근 권한을 요구하지 않는다. |

Google의 [Drive 권한 가이드](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)는 두 범위를 비민감 범위로 분류한다. [앱 데이터 폴더 가이드](https://developers.google.com/workspace/drive/api/guides/appdata)에 따르면 이 폴더는 Drive UI에서 보이지 않고 공유할 수 없으며, 앱 데이터 삭제 시 사라질 수 있다. 따라서 **공유 일지는 `appDataFolder`로 구현할 수 없다.** 공유 기능에는 별도 공유 저장소와 권한·키 관리 설계가 필요하다.

인증은 Google의 [데스크톱 OAuth 2.0 지침](https://developers.google.com/identity/protocols/oauth2/native-app)에 따라 시스템 브라우저, 임의 포트의 `127.0.0.1` 콜백, 요청마다 새로운 `state`와 PKCE S256 검증값을 쓴다. 내장 웹뷰에서 비밀번호를 받지 않는다. 앱에는 공개 가능한 데스크톱 OAuth 클라이언트 ID만 포함하고 클라이언트 비밀키는 넣지 않는다. 새로 고침 토큰은 Windows Credential Manager에 저장한다. 실제 배포 전 Google Cloud의 동의 화면 설정과 앱 검증 상태를 확인한다.

Google은 설치형 앱의 점진적 권한 부여를 지원하지 않는다. 보이는 백업을 활성화할 때는 `drive.appdata`와 `drive.file`을 함께 요청하는 별도의 전체 OAuth 인증을 수행하고, 실패해도 기존 동기화 연결은 유지한다.

## 데이터 형식과 암호화

- 로컬 저장소는 기록의 기준이다. 동기화 큐는 앱 DB의 트랜잭션으로 저장한다.
- 사용자 복구 구문에서 키 유도 함수로 동기화 마스터 키를 만들고, 각 파일은 새 난수 nonce를 사용한 인증 암호화로 보호한다. 키와 평문은 Drive에 올리지 않는다. 암호화 형식에는 버전, KDF 파라미터, nonce, 암호문, 인증 태그만 넣는다.
- 글은 `entry/<entry-id>/<revision-id>` 형태의 **불변 버전 파일**로 저장한다. 삭제는 삭제 표식 버전으로 기록한다. 각 버전은 부모 버전 ID와 기기 ID를 포함한다. 같은 글의 동시 편집은 한쪽을 조용히 덮어쓰지 않고 두 버전을 보존해 사용자에게 해결을 요청한다.
- 첨부 파일은 해시 기반 식별자와 별도 암호화 파일로 저장한다. 대용량 첨부는 재개 가능한 업로드를 사용하고 업로드 완료 전 글 버전을 게시하지 않는다.
- 원격 파일 이름과 메타데이터에는 제목·본문·태그·위치를 넣지 않는다. 로컬 검색 인덱스는 장치에서만 유지한다.
- 포맷·암호화 프로토콜 버전을 명시하고, 이전 버전을 읽을 수 있는 마이그레이션을 둔다. 암호화 설계는 구현 전 별도 검토가 필요하다.

### 구현 전 보안 조건

- 동기화 마스터 키는 암호학적 난수 256비트로 생성하고 복구 구문으로 인코딩한다. 사용자가 정한 짧은 암호를 그대로 암호화 키로 쓰지 않는다. 복구 구문을 잃으면 Google 계정만으로 복구할 수 없음을 연결 화면에서 알린다.
- 버전이 고정된 인증 암호화 형식을 사용한다. 객체 종류, 객체 ID, 버전 ID, 부모 버전 ID를 인증 데이터에 묶어 파일 바꿔치기와 메타데이터 변경을 검출한다. nonce는 키마다 재사용하지 않으며 암호화 라이브러리의 검증된 API를 사용한다.
- 암호문을 해독하기 전에 전체 크기, 항목 수, 압축 해제 크기, 포맷 버전을 제한한다. 인증 실패나 알 수 없는 버전은 동기화를 중단하고 원본 로컬 데이터를 유지한다.
- 복구 키와 OAuth 토큰은 로그, 오류 메시지, 원격 파일명, 분석 이벤트에 남기지 않는다. Windows Credential Manager는 같은 사용자 권한의 악성 프로그램까지 막는 보호 수단으로 간주하지 않는다.
- Google Drive의 이전 버전 복원·삭제·변조는 로컬에 보관한 마지막 확인 버전과 비교해 감지하고 사용자에게 알린다. 새 장치에서는 이 비교 기록이 없으므로 원격 데이터의 완전한 최신성을 보증할 수 없다는 한계를 알린다.
- OAuth 응답은 매 요청의 `state`, PKCE 검증값, 정확한 loopback 주소·포트를 확인한다. 동의받은 범위와 연결 계정을 표시하고, 범위 변경 시 추가 동의를 요구한다. 토큰은 연결 해제 시 로컬에서 제거하고 가능한 경우 서버에서도 폐기한다.
- 업로드 전에 로컬 파일 암호화와 암호화된 백업/복원 경로를 완성한다. 현재 버전의 `journal.json`, 미디어 파일, Documents 폴더의 JSON 백업은 평문이며 Google Drive 동기화 설계만으로 보호되지 않는다.

## 동기화 순서

1. 앱 시작 또는 수동 동기화에서 네트워크와 토큰 상태를 확인한다.
2. 첫 동기화는 `appDataFolder`의 앱 파일 목록을 읽는다. 이후에는 [Drive 변경 내역 API](https://developers.google.com/workspace/drive/api/guides/manage-changes)의 `getStartPageToken` / `changes.list`를 사용하며 `spaces=appDataFolder`로 범위를 제한한다.
3. 받은 암호문을 검증·해독한 뒤 로컬 트랜잭션으로 반영한다. **모든 변경을 로컬에 확정한 뒤에만** 새 페이지 토큰을 저장한다.
4. 로컬 전송 대기 버전과 미디어를 업로드한다. 실패한 항목은 지수 백오프로 재시도하고 사용자가 상태를 확인할 수 있게 한다.
5. 네트워크 끊김, 용량 부족, 토큰 만료, 다른 장치의 동시 수정, 파일 누락을 각각 다른 오류로 표시한다. 로컬 기록은 유지한다.

`changes.list`의 페이지를 모두 처리한 뒤 `newStartPageToken`을 보관한다는 규칙은 [Google 공식 변경 내역 가이드](https://developers.google.com/workspace/drive/api/guides/manage-changes)에 근거한다. 푸시 알림은 초기 버전의 필수 조건이 아니며, 앱 실행 중 주기적 확인과 수동 동기화로 시작한다.

## UI와 완료 기준

설정 화면에는 연결된 계정, 마지막 성공 시각, 업로드/다운로드 대기 건수, 충돌 건수, 사용 공간, 동기화 시작·일시 중지·연결 해제·복구 구문 관리 버튼을 둔다. 기록 화면에서는 저장 상태와 동기화 상태를 구분해 표시한다.

- 두 Windows PC에서 각각 오프라인으로 만든 글과 첨부가 재접속 후 양쪽에 나타난다.
- 같은 글을 동시에 수정하면 두 버전이 보존되고 충돌 해결 전 원본이 사라지지 않는다.
- 복구 구문이 없는 PC 및 Drive 웹 UI에서 본문과 첨부를 읽을 수 없다.
- 원격 용량 부족·권한 취소·토큰 만료 시에도 로컬 저장과 수동 백업이 동작한다.
- 연결 해제 후 원격 파일은 자동 삭제되지 않고, 로컬 기록도 유지된다.
- 같은 백업/변경을 두 번 받아도 글과 첨부가 중복 생성되지 않는다.

## 현재 앱과의 연결 지점

현재 Rust 앱의 로컬 `Entry`·`Attachment`·`Journal` 모델 위에 `SyncRevision`, `SyncQueue`, `RemoteFile`, `SyncCursor`를 추가한다. 지금의 `journal.json` 저장은 단일 파일이므로 동기화 구현 전에 트랜잭션 가능한 SQLite로 옮긴다. 현재 앱 잠금은 파일 암호화가 아니므로, Google Drive 업로드 기능은 암호화 저장과 키 복구가 완성되기 전까지 활성화하지 않는다.
